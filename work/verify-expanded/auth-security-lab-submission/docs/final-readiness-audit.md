# 제출 전 보안 범위 재점검

## 최종 판정

정의한 논문 범위의 16개 시나리오는 모두 취약 모드와 강화 모드에 구현되어 있다. 각 시나리오는 판정 함수 기반 비교 테스트를 가지며, 16개 모두 실제 API·DB·암호 또는 쿠키 흐름을 사용하는 통합 테스트도 가진다. 최신 전체 실행은 72/72 통과했다.

다만 “알려진 모든 웹 공격”을 다뤘다는 표현은 사용하지 않는다. 본 연구는 인증·세션·권한·토큰 및 요청 흐름으로 범위를 제한한다. SQL 삽입, XSS, SSRF, 파일 업로드, 역직렬화, 공급망, 네트워크·운영체제 공격은 연구 대상이 아니다.

## 방어 구현의 경계

- 속도 제한 상태는 단일 Node.js 프로세스 메모리에 있다. 여러 서버 인스턴스에서는 Redis 같은 공유 저장소가 필요하다.
- 테스트를 위해 `x-forwarded-for` 입력으로 출처를 구분한다. 운영 배포에서는 신뢰 프록시가 덮어쓴 값만 사용해야 한다.
- Secure 쿠키는 HTTPS에서만 브라우저가 전송한다. 현재 HTTP localhost 테스트는 세션 토큰 헤더를 실험용 통로로 함께 사용한다.
- 비밀번호 정책은 길이와 대표 상용 문자열을 검사한다. 운영 수준에서는 유출 비밀번호 차단 목록과 MFA가 필요하다.
- 비밀번호 재설정 발급 API의 `labToken` 응답은 로컬 자동화 실험용이다. 운영 환경에서는 이메일 등 별도 채널로만 전달해야 한다.
- JWT는 HS256, iss, aud, exp 검증을 적용했다. 키 회전, 다중 발급자, nbf 실패 사례는 추가 연구 항목이다.
- 감사 로그 집계값은 여러 실행의 누적치다. 단일 회차 성공률 계산에는 Playwright 회차별 결과를 사용한다.
- `x-session-token` 헤더는 자동화 실험 편의를 위한 인터페이스다. 실제 서비스 설계에서는 안전한 쿠키 또는 표준 Authorization 헤더 하나로 제한한다.

## 제출 전 남은 연구 작업

기능 구현은 현재 16개 범위를 충족한다. 논문 결과의 신뢰도를 높이려면 동일 실험을 최소 10회 반복하여 회차별 성공률과 응답시간을 저장해야 한다. 제출 과제에서 요구하는 분량, 장 구성, 인용 형식, 표·그림 수가 제시되면 그 형식에 맞춰 최종 원고와 부록을 생성한다.
