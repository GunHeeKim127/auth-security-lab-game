# 웹 애플리케이션의 인증·인가 우회 경로 분석 및 다중 보안 통제 적용에 따른 취약점 개선 효과 평가

작성자: 김건희  
작성일: 2026-10-12

## 초록

본 연구는 웹 애플리케이션의 인증·인가 우회 경로를 공격 입력, 취약 검증 지점, 도달 자산, 공격 결과의 연쇄로 분석하고 인증·인가 강화만으로 충분한지와 다중 보안 통제의 추가 효과를 측정했다. Next.js, PostgreSQL, Prisma, Playwright로 본인 소유의 로컬 실험 환경을 만들고 사용자 열거, 무차별 대입, 세션 고정, 객체 단위 권한 우회, JWT 알고리즘 변조, 재설정 토큰 재사용, CSRF 등 16개 경로에 같은 공격 입력을 적용했다. 실험 조건은 모든 통제가 없는 취약 모드, 인증·인가의 8개 경로만 강화한 부분 강화 모드, 세션·토큰·요청 흐름까지 강화한 전체 강화 모드의 세 가지다. 각 경로를 조건별로 10회 반복해 총 480건을 수집했다. 공격 성공률은 취약 모드 160/160, 부분 강화 모드 80/160, 전체 강화 모드 0/160으로 100%, 50%, 0%였다. 부분 강화 모드는 인증·인가 공격 80건을 모두 막았지만 세션·토큰·요청 흐름 공격 80건은 모두 성공했다. 이 결과는 인증·인가 강화가 필요하지만 충분하지 않으며 전체 우회 경로에 다중 통제가 필요하다는 가설을 지지한다.

## 1 서론

### 1.1 관심 분야와 문제의식

관심 분야는 웹 애플리케이션의 인증·인가 우회 경로와 여러 방어 통제를 함께 적용했을 때의 개선 효과다. 보안 권고를 나열하는 데 그치지 않고 공격자가 어떤 입력으로 어느 검증 지점을 통과해 어떤 자산에 도달하는지 경로를 모델링하고, 같은 입력을 취약 구현과 강화 구현에 적용해 차이를 원자료로 남기는 것이 목적이다. 본 연구에서 인증은 신원 확인, 인가는 인증된 주체가 특정 자원이나 기능을 사용할 수 있는지에 대한 서버 측 결정을 뜻한다. 세션과 토큰은 두 결정을 연결하거나 우회하는 매개로 다룬다.

### 1.2 이 주제를 선택한 이유

웹 애플리케이션에서는 로그인 성공 여부만 안전하다고 해서 전체 인증 체계가 안전해지지 않는다. 인증 뒤에 발급된 세션이 고정·재사용되거나, 인증된 일반 사용자가 타인의 객체 식별자를 바꾸거나 관리자 API를 직접 호출하거나, 서명과 출처 검증이 빠진 토큰과 요청이 수락되면 인증 절차를 거치고도 보호 자산에 도달할 수 있다. 이런 문제는 화면에서 기능을 숨기는 것만으로 확인하거나 해결하기 어렵고 서버의 여러 경계에서 이어지는 경로로 보아야 한다.

이 주제를 선택한 직접적인 이유는 보안 지침의 목록을 암기하는 대신 취약 구현과 방어 구현을 같은 애플리케이션 안에 만들어 실제 차이를 숫자로 확인하고 싶었기 때문이다. 인증, 세션, 인가, 토큰, 요청 출처는 서로 연결되어 있으므로 한 가지 방어만 보는 연구보다 다중 통제의 결합 효과를 보는 편이 실제 개발 의사결정에 가깝다고 판단했다. 또한 로컬 환경에서 소유한 코드와 테스트 계정만 사용하면 외부 시스템에 피해를 주지 않고 일주일 안에 원자료를 직접 수집하고 다른 사람이 재현할 수 있다. 따라서 본 연구는 “어떤 우회 경로가 존재하는가”, “어느 서버 경계에서 차단해야 하는가”, “여러 통제를 적용했을 때 성공률이 얼마나 변하는가”를 함께 답하도록 설계했다.

### 1.3 질문을 가설로 좁힌 과정

AI와 함께 검토한 질문은 다음 열 가지였다. (1) 동일 계정의 반복 로그인 제한은 무차별 대입 성공을 낮추는가, (2) 균일한 로그인 오류는 사용자 열거를 막는가, (3) 긴 비밀번호와 차단 목록은 약한 비밀번호 등록을 줄이는가, (4) 로그인 후 세션 ID 재발급은 세션 고정을 막는가, (5) 서버 측 세션 폐기는 로그아웃 토큰 재사용을 막는가, (6) 객체 소유권 검사는 IDOR를 막는가, (7) 역할 검사는 관리자 기능 우회를 막는가, (8) JWT 알고리즘 고정은 alg 변조를 막는가, (9) 단일 사용 재설정 토큰은 재사용을 막는가, (10) Origin과 CSRF 토큰 검사는 교차 출처 상태 변경을 막는가. 각 질문에 대해 측정 가능성, 일주일 내 수집 가능성, 반대 결과의 의미를 확인했다. 모두 로컬 API의 공격 성공 여부와 상태 코드로 측정할 수 있어 하나의 비교 실험으로 묶었다.

접은 후보는 세 가지다. 첫째, Docker와 Windows 로컬 실행의 재현성 비교는 환경 구축 시간이 결과를 크게 좌우하고 보안 통제 효과라는 관심 분야에서 벗어나 접었다. 둘째, 비밀번호 정책만 비교하는 연구는 일주일 안에 가능하지만 세션과 권한 우회를 설명하지 못해 범위가 지나치게 좁었다. 셋째, OWASP 문헌만 정리하는 연구는 직접 수집한 원자료가 없어 실험 과제의 목적을 충족하지 못했다. 추가로 모든 웹 공격을 다루는 후보는 공격 표면이 너무 커 같은 조건을 유지할 수 없어 제외했다.

### 1.4 최종 가설과 반증 조건

최종 가설은 다음 한 문장이다. **동일한 16개 우회 경로를 적용할 때 인증·인가만 강화한 부분 강화 모드는 해당 경로의 공격은 줄이지만 세션·토큰·요청 흐름의 공격 성공을 남기며, 예방·억제·회복·감사 계층을 모두 적용한 전체 강화 모드는 부분 강화 모드보다 전체 공격 성공률을 더 낮춘다.** 독립 변수는 실행 모드의 세 수준인 취약, 인증·인가 부분 강화, 전체 강화이고 종속 변수는 공격 성공률이다. 공격 성공은 의도하지 않은 인증, 세션 재사용, 타인 자원 접근·변경, 변조 토큰 수락 또는 교차 출처 상태 변경이 허용된 경우로 정의했다. 취약점 개선 효과는 조건 간 공격 성공률의 퍼센트포인트 차이로 측정했다. 부분 강화 모드에서 세션·토큰·요청 흐름 공격까지 차단되거나, 전체 강화 모드가 부분 강화보다 성공률을 낮추지 못하면 가설은 지지되지 않는다. 데이터 수집 범위는 2026-10-12 하루 동안의 로컬 환경, 16개 경로, 세 조건별 10회다.

## 2 선행 연구와 논거

Florêncio와 Herley의 50만 사용자·3개월 비밀번호 사용 연구는 비밀번호 재사용이 실제로 관찰되는 현상임을 보여 주어 자격 증명 스터핑 시나리오의 현실적 근거를 제공한다. OWASP Top 10의 접근 통제 자료는 기여 데이터셋에서 접근 통제 문제가 광범위하게 관찰됐다고 보고하여 객체 소유권과 역할 검사 실험의 필요성을 뒷받침한다. NIST SP 800-63B는 인증 시도 속도 제한과 비밀번호 차단 목록 등 인증자 관리 요구를 제시해 AUTH-02와 AUTH-03의 통제 선택을 뒷받침한다. Sheffer, Hardt, Jones의 RFC 8725는 JWT 처리에서 허용 알고리즘을 명시적으로 검증하도록 요구해 TOKEN-01의 알고리즘 고정 통제를 뒷받침한다. OWASP의 세션 관리 및 CSRF 지침은 세션 ID 재발급, 쿠키 속성, 서버 측 무효화와 CSRF 토큰·Origin 검사의 설계 근거다.

이미 알려진 사실은 비밀번호 재사용이 관찰되고, 접근 통제 결함이 널리 보고되며, 속도 제한·소유권 검사·알고리즘 고정·CSRF 검사가 권고된다는 점이다. 본 연구가 새로 주장하는 범위는 인증·인가 우회 과정을 16개 경로로 구조화하고 이 권고들을 예방·억제·회복·감사 계층으로 한 로컬 코드베이스에 결합한 뒤 동일 입력을 10회 반복했을 때 관찰된 개선 효과다. 실제 인터넷 전체의 침해율이나 각 통제의 단독 효과를 새로 주장하지 않는다.

문헌은 제목, 저자, 연도, 발행 기관 또는 학술회의, 원문 URL, 초록이나 규범 조항을 직접 확인했다. AI가 제안하거나 검색 결과에 나타난 Wikipedia의 JWT 문서와 2026년 YouTube NIST 해설 영상은 2차 자료이고 내용이 바뀔 수 있어 근거 목록에서 제외했다. 존재 여부와 저자를 확인할 수 없는 블로그 글도 제외했다.

## 3 방법

### 3.1 실험 환경

Windows 로컬 컴퓨터에서 Node.js 20.9.0, Next.js 15.5.27, Prisma 6.19.3, PostgreSQL 15, Playwright를 사용했다. 취약 모드는 127.0.0.1:3001, 강화 모드는 127.0.0.1:3002에서 실행했다. 외부 시스템, 실제 사용자 계정, 공개 서비스에는 요청하지 않았다.

### 3.2 변수와 통제

바꾼 조건은 `LAB_MODE`의 취약, `auth-authz-only`, 전체 강화 값이다. 부분 강화 조건은 AUTH와 AUTHZ 경로에만 강화 판정을 적용하고 SESS, TOKEN, FLOW 경로는 취약 상태로 유지했다. 고정 조건은 애플리케이션 버전, 데이터베이스 구조, 시나리오별 공격 입력, 로컬 호스트, 브라우저 자동화 도구, 시나리오 수다. 측정값은 회차, 시나리오 ID, 모드, 공격 성공 여부, HTTP 상태, 응답시간, 판정 근거, 통제 설명, 관찰 시각이다. 16개 경로를 세 조건에서 10회 반복하여 계획 표본은 16×3×10=480건이다.

### 3.3 인증·인가 우회 경로

각 우회 경로는 `공격 입력 → 취약한 검증 지점 → 보호 자산 또는 기능 → 성공 결과` 순서로 분석했다. 인증 경로는 계정 식별·시도 제한·비밀번호 검증을 우회해 계정 정보를 알아내거나 인증 기회를 늘린다. 세션 경로는 식별자 재발급·쿠키 속성·폐기·만료 검증을 우회해 인증 상태를 재사용한다. 인가 경로는 소유권과 역할 검사를 우회해 타인의 자원이나 관리자 기능에 도달한다. 토큰·요청 경로는 서명 알고리즘·보안 변경 시점·단일 사용·요청 출처 검증을 우회해 변조 또는 재사용된 요청을 승인받는다.

### 3.4 다중 보안 통제 적용 모델

강화 모드는 하나의 통제에 의존하지 않고 경로의 서로 다른 지점에 통제를 배치했다. 예방 계층은 균일 오류, 비밀번호 정책, 소유권·역할 검사, JWT 알고리즘 고정, Origin·CSRF 검사를 포함한다. 억제 계층은 로그인 시도 속도 제한과 토큰 만료 검증으로 공격 기회와 유효 시간을 줄인다. 회복 계층은 로그인 후 세션 ID 재발급, 로그아웃·비밀번호 변경 시 세션 폐기, 재설정 토큰 단일 사용으로 이미 발급된 인증 수단의 재사용을 차단한다. 감사 계층은 시나리오, 모드, 결과와 판정 근거를 PostgreSQL에 기록해 경로별 결과를 추적한다. 여기서 “다중 통제 효과”는 이 묶음 전체의 전후 차이를 뜻하며 개별 통제 하나의 인과 효과를 뜻하지 않는다.

### 3.5 취약점별 원인과 해결 근거

AUTH-01은 계정 존재 여부에 따라 로그인 오류가 달라 사용자 열거가 가능한 취약점이다. 강화 모드는 존재 여부와 무관한 동일한 401 응답을 사용했다. 공격자에게 유효 계정 목록을 만들 수 있는 구별 신호를 주지 않기 위해서다. AUTH-02는 로그인 실패를 제한하지 않아 비밀번호를 계속 추측할 수 있는 문제로, 계정·출처별 5회 초과 요청을 429로 제한했다. 비밀번호가 충분히 길어도 온라인 시도 횟수를 줄이지 않으면 추측 기회가 계속 누적되기 때문이다. AUTH-03은 짧거나 흔한 비밀번호를 허용하는 문제로, 최소 15자와 대표 상용 문자열 차단을 적용했다. 복잡성 기호 강제보다 길이와 알려진 약한 값의 거부가 실험 입력을 직접 차단하기 때문이다. AUTH-04는 같은 출처가 여러 계정에 재사용 비밀번호를 대입하는 자격 증명 스터핑으로, 계정별 제한과 별개로 출처 단위 누적 제한을 적용했다. 계정만 기준으로 제한하면 공격자가 대상을 순환해 우회할 수 있기 때문이다.

SESS-01은 공격자가 지정한 세션 식별자가 로그인 뒤에도 유지되는 세션 고정으로, 인증 성공 시 새 난수 세션을 발급하고 이전 식별자를 무효화했다. 권한 수준이 바뀌는 시점에 기존 식별자와의 연결을 끊기 위해서다. SESS-02는 쿠키에 HttpOnly·Secure·SameSite가 빠진 문제로 세 속성을 강제했다. 각각 스크립트 접근, 평문 전송, 교차 사이트 요청에서 노출 가능성을 줄이는 서로 다른 역할을 하기 때문이다. SESS-03은 로그아웃한 토큰이 계속 사용되는 문제로 DB 세션을 폐기했다. 클라이언트 쿠키 삭제만으로는 이미 복사된 토큰을 무효화할 수 없기 때문이다. SESS-04는 만료시간이 지난 세션 수락으로, 모든 보호 요청에서 서버가 만료시간을 검사했다. 만료 정보가 있어도 사용 시점에 검증하지 않으면 통제가 되지 않기 때문이다.

AUTHZ-01은 객체 ID 변경으로 타인의 자원을 조회하는 수평 권한 우회이고, AUTHZ-03과 AUTHZ-04는 같은 방식의 수정·삭제 우회다. 세 경우 모두 서버가 현재 사용자와 자원 소유자를 비교하고 관리자 예외를 명시적으로 검사했다. URL이나 본문에 포함된 사용자·객체 식별자는 공격자가 바꿀 수 있으므로 클라이언트 값을 권한 근거로 신뢰할 수 없기 때문이다. AUTHZ-02는 일반 사용자가 관리자 API를 직접 호출하는 수직 권한 우회로, 라우트 내부에서 ADMIN 역할을 검사했다. 화면에서 버튼을 숨기는 것은 직접 HTTP 요청을 막지 못하기 때문이다.

TOKEN-01은 `alg=none`처럼 공격자가 선택한 JWT 알고리즘을 수락하는 문제로, HS256만 허용하고 서명·발급자·수신자·만료를 함께 검증했다. 토큰 헤더는 신뢰 경계 밖의 입력이므로 서버 정책이 허용 알고리즘을 결정해야 하기 때문이다. TOKEN-02는 비밀번호 변경 전 발급된 인증 수단이 계속 유효한 문제로, 변경 시 활성 세션을 모두 폐기했다. 보안 변경 뒤 탈취 토큰의 유효성을 끝내기 위해서다. FLOW-01은 비밀번호 재설정 토큰의 두 번째 사용을 허용하는 문제로 토큰 해시 저장, 15분 만료, 사용 시각 기록을 적용했다. 원문 노출을 줄이고 재전송과 시간 초과를 모두 막기 위해서다. FLOW-02는 공격자 출처의 상태 변경 요청을 허용하는 CSRF로, 인증 확인과 함께 Origin 및 쿠키·헤더 CSRF 토큰 일치를 검사했다. 브라우저의 자동 쿠키 전송만으로는 사용자의 의도를 증명할 수 없기 때문이다.

### 3.6 실행 절차와 설계 변경

Playwright가 포트 3001의 취약 서버, 3003의 인증·인가 부분 강화 서버, 3002의 전체 강화 서버를 시작하고 같은 JSON 공격 입력을 `/api/lab/{시나리오ID}`에 보냈다. 세 모드의 시작 순서를 회차별로 순환해 특정 모드가 항상 먼저 실행되지 않도록 했다. 처음에는 취약·전체 강화의 두 조건만 비교했으나, 그 설계로는 인증·인가 강화의 불충분성을 확인할 수 없다는 검토에 따라 부분 강화 조건을 추가했다. 이전 결과는 삭제하지 않고 별도 JSON과 문서에 남겼다. 최종 원자료 파일은 정확히 480건을 포함한다.

## 4 결과

취약 모드 160건은 모두 공격 성공으로 판정됐다. 인증·인가 부분 강화 모드는 인증 40건과 인가 40건을 모두 차단했지만 세션 40건과 토큰·요청 흐름 40건은 모두 성공해 총 80/160건, 50%의 공격 성공률을 보였다. 전체 강화 모드는 160건을 모두 차단해 성공률이 0%였다. 따라서 취약에서 부분 강화로 50%포인트, 부분 강화에서 전체 강화로 다시 50%포인트, 취약에서 전체 강화로 100%포인트 개선됐다. 이 중 부분 강화 상태에서 남은 80건은 정상적인 로그인·역할 검사를 통과했거나 이를 직접 공격하지 않고 세션 고정·재사용, 변조 JWT, 재설정 토큰 재사용, CSRF 같은 다른 신뢰 경계를 공격한 결과다. 응답시간 중앙값은 취약 65.40ms, 부분 강화 66.04ms, 전체 강화 64.50ms였으며 성능 우열을 판단하도록 설계하지 않았으므로 탐색적 수치로만 사용했다.

가설대로 부분 강화 모드에서는 인증·인가 공격만 차단되고 나머지 공격은 그대로 성공했다. 이는 강한 로그인 정책과 서버 측 객체 권한 검사가 세션 식별자, 토큰 수명과 무결성, 재설정 흐름, 요청 출처의 별도 검증을 대신하지 못함을 보여 준다. 전체 강화에서만 16개 경로가 모두 차단됐다. 수치가 100%, 50%, 0%로 정확히 분리된 이유는 각 범주가 4개 경로로 균등하고 부분 강화가 네 범주 중 인증과 인가 두 범주에만 적용됐기 때문이다. 따라서 50%라는 값은 보편적인 산업 평균이 아니라 이 균형 설계에서 나온 값이다.

초기 가설은 “보안 통제를 적용하면 웹 공격이 방어된다”였고 두 모드만 비교했다. 이 설계는 인증·인가 강화만으로 충분한지 확인하지 못한다는 검토를 거쳐 세 모드 가설로 수정했다. 최종 가설은 인증·인가 부분 강화에서 남는 우회 경로와 전체 다중 통제의 추가 감소를 구분한다. 원자료의 세 모드별 성공 건수와 경로별 10회 결과가 최종 판단의 직접 근거다.

## 5 논의

결과는 정의한 16개 인증·인가 우회 경로와 로컬 구현 범위에서 다중 보안 통제가 공격 성공률을 낮춘다는 가설을 지지한다. 경로 분석 결과 취약 모드의 공통 원인은 클라이언트가 제공한 계정 정보, 세션 식별자, 사용자·역할 값, JWT 헤더, 요청 출처를 서버가 충분히 재검증하지 않는 데 있었다. 강화 모드는 경로 앞단의 입력·출처 검증, 결정 지점의 소유권·역할·서명 검증, 사후 단계의 만료·폐기·감사 기록을 결합해 보호 자산에 이르기 전에 요청을 차단했다. 차단 상태는 원인에 맞춰 401, 403, 410, 422, 429 등으로 나타났고, 이는 단순 UI 숨김이 아니라 서버 경계에서 요청이 거부됐음을 보여 준다.

### 5.1 수치로 답할 수 있는 연구 결론

첫째, 공격 성공률은 취약 100%, 인증·인가 부분 강화 50%, 전체 강화 0%였다. 둘째, 부분 강화는 적용 대상인 인증·인가에서 80/80건을 차단했지만 적용하지 않은 세션·토큰·요청 흐름에서는 80/80건을 허용했다. 셋째, 전체 강화는 남은 80건도 차단해 부분 강화 대비 50%포인트의 추가 개선을 보였다. 넷째, 16개 경로 모두 각 조건의 10회에서 같은 결과를 보여 실행 안정성은 확인됐다. 이 결과는 인증·인가 강화가 필요조건이지만 충분조건은 아니라는 수치적 근거다. 반복 관찰이 서로 독립적인 실제 공격 표본은 아니므로 통계적 유의성이나 실서비스 침해 확률로 해석하지 않는다.

### 5.2 왜 개선되었고 어떻게 해결했는가

개선의 공통 원인은 신뢰 결정을 클라이언트에서 서버로 옮긴 것이다. 입력 단계에서는 계정 오류와 비밀번호·출처를 검증했고, 인증 상태 단계에서는 세션을 재발급하고 만료·폐기를 확인했으며, 인가 단계에서는 요청마다 자원 소유권과 역할을 검사했다. 토큰 단계에서는 공격자가 제공한 알고리즘을 그대로 따르지 않고 서버의 허용 목록, 서명, 발급자, 수신자와 수명을 확인했다. 이미 발급된 수단은 로그아웃·비밀번호 변경·재설정 토큰 소비 시 서버 상태를 바꿔 재사용을 막았다. 한 통제가 실패하더라도 다음 경계가 남도록 여러 계층을 연결한 것이 단일 화면 제어나 클라이언트 검사보다 안정적인 해결책이었다.

### 5.3 제안하는 후속 연구와 개발 방향

첫 번째 후속 실험은 절제 실험이다. 강화 모드에서 통제를 하나씩 제거하고 각 조건을 10회 이상 반복하면 균일 오류, 속도 제한, 소유권 검사, 세션 폐기 등 개별 통제가 어느 경로에 얼마나 기여하는지 분리할 수 있다. 두 번째는 입력 변형 실험이다. 독립 연구자가 새로운 계정 순환 방식, 객체 ID 조합, JWT 헤더, Origin·토큰 불일치 조합을 작성해 현재 통제에 과적합되지 않았는지 확인한다. 세 번째는 운영 환경 근접 실험이다. HTTPS와 실제 브라우저 쿠키, Redis 기반 분산 속도 제한, 프록시가 정규화한 클라이언트 주소, 키 회전과 다중 인스턴스를 사용한다. 네 번째는 방어 기능 확장으로 MFA, 유출 비밀번호 차단 목록, 세션·키 회전, 이상 징후 경보를 추가한다. 각 단계는 공격 성공률뿐 아니라 정상 요청 성공률, 오탐률, 지연시간과 운영 비용을 함께 측정해야 한다.

그러나 본 실험의 공격 판정은 재현성을 위해 결정적으로 설계되어 같은 입력에 같은 결과를 낸다. 표본 10회는 실행 안정성을 확인하지만 인터넷 환경의 공격 확률을 추정하는 표본은 아니다. 다중 통제를 묶어서 적용했으므로 성공률 감소를 특정 통제 하나에 귀속할 수 없고, 통제를 하나씩 제거하는 절제 실험도 수행하지 않았다. 단일 Windows 컴퓨터와 단일 Node.js 프로세스를 사용했고 속도 제한은 메모리 기반이므로 다중 인스턴스 환경을 검증하지 않았다. HTTP localhost에서는 Secure 쿠키의 실제 전송 조건을 완전히 재현하지 못했다. MFA, 유출 비밀번호 대규모 차단 목록, 키 회전, 다중 발급자, `nbf`, 분산 속도 제한은 포함하지 않았다. SQL 삽입, XSS, SSRF, 파일 업로드, 역직렬화, 공급망, 네트워크와 운영체제 공격도 연구 범위 밖이다. 따라서 “모든 공격을 방어했다”, “각 통제가 동일한 효과를 냈다” 또는 “실서비스 침해가 0%가 된다”는 결론은 내릴 수 없다.

## 6 결론

동일한 16개 우회 경로를 세 조건에서 각각 10회 적용한 480건의 원자료에서 공격 성공률은 취약 100%, 인증·인가 부분 강화 50%, 전체 강화 0%였다. 부분 강화는 인증·인가 경로를 모두 막았지만 세션·토큰·요청 흐름의 8개 경로는 80/80건 모두 성공했다. 따라서 로그인과 객체 권한을 강하게 만드는 것만으로 세션 재사용, 토큰 변조, 복구 흐름과 CSRF까지 보호할 수 없으며, 각 신뢰 경계에 맞는 다중 통제가 필요하다. 전체 강화는 부분 강화 대비 50%포인트, 취약 대비 100%포인트의 추가 개선을 보였다. 이 결론은 균등하게 구성한 16개 경로와 현재 코드베이스의 범위로 제한된다.

## AI와 본인의 판단

AI는 후보 질문 정리, 코드와 테스트 초안, 반복 실행 자동화, 표와 문장 정리를 맡았다.  
본인은 최종 가설과 연구 범위를 선택하고 로컬 데이터베이스를 구성했으며, 어떤 결과를 근거로 결론을 받아들일지 판단했다.  
AI가 계산한 집계는 원자료 480건과 자동화 테스트로 다시 확인했고, 부분 강화 조건의 필요성과 과도한 일반화를 제외하는 최종 판단은 본인이 수행했다.
