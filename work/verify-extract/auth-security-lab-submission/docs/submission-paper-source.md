# 서버 측 보안 통제가 웹 인증 공격 성공률에 미치는 영향

작성자: kimgu  
작성일: 2026-10-12

## 초록

본 연구는 웹 인증·세션·권한·토큰·요청 흐름에서 취약 구현과 서버 측 보안 통제 적용 구현의 공격 성공률 차이를 측정했다. Next.js, PostgreSQL, Prisma, Playwright로 본인 소유의 로컬 실험 환경을 만들고 사용자 열거, 무차별 대입, 세션 고정, 객체 단위 권한 우회, JWT 알고리즘 변조, 재설정 토큰 재사용, CSRF 등 16개 시나리오에 같은 공격 입력을 적용했다. 각 시나리오를 취약·강화 모드에서 10회 반복하여 총 320건을 수집했다. 취약 모드는 160/160건에서 공격이 성공했고 강화 모드는 0/160건에서 성공하여 공격 성공률이 100%에서 0%로 감소했다. 이 결과는 정의한 입력과 로컬 구현 범위에서 서버 측 통제가 공격 성공률을 낮춘다는 가설을 지지한다. 다만 결정적 판정 로직, 단일 컴퓨터, 제한된 공격 집합을 사용했으므로 실제 인터넷 서비스의 침해율이나 모든 웹 공격으로 일반화할 수 없다.

## 1 서론

### 1.1 관심 분야와 문제의식

관심 분야는 웹 애플리케이션의 인증, 세션, 권한 관리와 방어 통제의 효과다. 보안 권고를 나열하는 데 그치지 않고 같은 공격 입력을 취약 구현과 강화 구현에 적용해 차이를 원자료로 남기는 것이 목적이다.

### 1.2 질문을 가설로 좁힌 과정

AI와 함께 검토한 질문은 다음 열 가지였다. (1) 동일 계정의 반복 로그인 제한은 무차별 대입 성공을 낮추는가, (2) 균일한 로그인 오류는 사용자 열거를 막는가, (3) 긴 비밀번호와 차단 목록은 약한 비밀번호 등록을 줄이는가, (4) 로그인 후 세션 ID 재발급은 세션 고정을 막는가, (5) 서버 측 세션 폐기는 로그아웃 토큰 재사용을 막는가, (6) 객체 소유권 검사는 IDOR를 막는가, (7) 역할 검사는 관리자 기능 우회를 막는가, (8) JWT 알고리즘 고정은 alg 변조를 막는가, (9) 단일 사용 재설정 토큰은 재사용을 막는가, (10) Origin과 CSRF 토큰 검사는 교차 출처 상태 변경을 막는가. 각 질문에 대해 측정 가능성, 일주일 내 수집 가능성, 반대 결과의 의미를 확인했다. 모두 로컬 API의 공격 성공 여부와 상태 코드로 측정할 수 있어 하나의 비교 실험으로 묶었다.

접은 후보는 세 가지다. 첫째, Docker와 Windows 로컬 실행의 재현성 비교는 환경 구축 시간이 결과를 크게 좌우하고 보안 통제 효과라는 관심 분야에서 벗어나 접었다. 둘째, 비밀번호 정책만 비교하는 연구는 일주일 안에 가능하지만 세션과 권한 우회를 설명하지 못해 범위가 지나치게 좁었다. 셋째, OWASP 문헌만 정리하는 연구는 직접 수집한 원자료가 없어 실험 과제의 목적을 충족하지 못했다. 추가로 모든 웹 공격을 다루는 후보는 공격 표면이 너무 커 같은 조건을 유지할 수 없어 제외했다.

### 1.3 최종 가설과 반증 조건

최종 가설은 다음 한 문장이다. **동일한 16개 공격 입력을 Next.js와 PostgreSQL 기반 로컬 웹 애플리케이션에 적용할 때 서버 측 인증·세션·권한 통제를 적용한 강화 모드는 취약 모드보다 공격 성공률을 낮춘다.** 독립 변수는 실행 모드이고 종속 변수는 공격 성공률이다. 공격 성공은 의도하지 않은 인증, 세션 재사용, 타인 자원 접근·변경, 변조 토큰 수락 또는 교차 출처 상태 변경이 허용된 경우로 정의했다. 강화 모드 성공률이 취약 모드보다 낮지 않거나 일부 시나리오에서 10회 모두 그대로 성공하면 가설은 지지되지 않는다. 데이터 수집 범위는 2026-10-12 하루 동안의 로컬 환경, 16개 시나리오, 모드별 10회다. 이 가설은 동일 입력·동일 코드베이스에서 통제 적용 여부만 바꿀 수 있고, 틀린 결과도 방어 실패로 해석할 수 있어 최종 선택했다.

## 2 선행 연구와 논거

Florêncio와 Herley의 50만 사용자·3개월 비밀번호 사용 연구는 비밀번호 재사용이 실제로 관찰되는 현상임을 보여 주어 자격 증명 스터핑 시나리오의 현실적 근거를 제공한다. OWASP Top 10의 접근 통제 자료는 기여 데이터셋에서 접근 통제 문제가 광범위하게 관찰됐다고 보고하여 객체 소유권과 역할 검사 실험의 필요성을 뒷받침한다. NIST SP 800-63B는 인증 시도 속도 제한과 비밀번호 차단 목록 등 인증자 관리 요구를 제시해 AUTH-02와 AUTH-03의 통제 선택을 뒷받침한다. Sheffer, Hardt, Jones의 RFC 8725는 JWT 처리에서 허용 알고리즘을 명시적으로 검증하도록 요구해 TOKEN-01의 알고리즘 고정 통제를 뒷받침한다. OWASP의 세션 관리 및 CSRF 지침은 세션 ID 재발급, 쿠키 속성, 서버 측 무효화와 CSRF 토큰·Origin 검사의 설계 근거다.

이미 알려진 사실은 비밀번호 재사용이 관찰되고, 접근 통제 결함이 널리 보고되며, 속도 제한·소유권 검사·알고리즘 고정·CSRF 검사가 권고된다는 점이다. 본 연구가 새로 주장하는 범위는 이 권고들을 한 로컬 코드베이스의 16개 시나리오에 구현하고 동일 입력을 10회 반복했을 때 관찰된 공격 성공률 차이다. 실제 인터넷 전체의 침해율을 새로 주장하지 않는다.

문헌은 제목, 저자, 연도, 발행 기관 또는 학술회의, 원문 URL, 초록이나 규범 조항을 직접 확인했다. AI가 제안하거나 검색 결과에 나타난 Wikipedia의 JWT 문서와 2026년 YouTube NIST 해설 영상은 2차 자료이고 내용이 바뀔 수 있어 근거 목록에서 제외했다. 존재 여부와 저자를 확인할 수 없는 블로그 글도 제외했다.

## 3 방법

### 3.1 실험 환경

Windows 로컬 컴퓨터에서 Node.js 20.9.0, Next.js 15.5.27, Prisma 6.19.3, PostgreSQL 15, Playwright를 사용했다. 취약 모드는 127.0.0.1:3001, 강화 모드는 127.0.0.1:3002에서 실행했다. 외부 시스템, 실제 사용자 계정, 공개 서비스에는 요청하지 않았다.

### 3.2 변수와 통제

바꾼 조건은 `LAB_MODE`의 취약·강화 값이다. 고정 조건은 애플리케이션 버전, 데이터베이스 구조, 시나리오별 공격 입력, 로컬 호스트, 브라우저 자동화 도구, 시나리오 수다. 측정값은 회차, 시나리오 ID, 모드, 공격 성공 여부, HTTP 상태, 응답시간, 판정 근거, 통제 설명, 관찰 시각이다. 각 16개 시나리오를 두 모드에서 10회 반복하여 계획 표본은 16×2×10=320건이다.

### 3.3 시나리오

인증은 사용자 열거, 반복 비밀번호 대입, 약한 비밀번호 등록, 자격 증명 스터핑을 포함한다. 세션은 세션 고정, 보호되지 않은 쿠키, 로그아웃 토큰 재사용, 만료 토큰을 포함한다. 권한은 타인 객체 조회·수정·삭제와 관리자 기능 우회를 포함한다. 토큰·요청 흐름은 JWT alg 변조, 비밀번호 변경 전 토큰 재사용, 재설정 토큰 재사용, CSRF를 포함한다.

### 3.4 실행 절차와 설계 변경

Playwright가 두 서버를 시작하고 같은 JSON 공격 입력을 `/api/lab/{시나리오ID}`에 보냈다. 홀수 회차는 취약 후 강화, 짝수 회차는 강화 후 취약 순서로 실행해 순서 효과를 줄였다. 처음에는 각 시나리오를 한 번 비교했으나 과제의 최소 10회 반복 기준과 우연 구분 요구를 확인한 뒤 10회로 변경했다. 이전 결과는 삭제하지 않고 별도 JSON과 문서에 남겼다. 최종 원자료 파일은 정확히 320건을 포함한다.

## 4 결과

취약 모드 160건은 모두 공격 성공으로 판정됐고 강화 모드 160건은 모두 차단됐다. 따라서 공격 성공률은 100%와 0%였으며 차이는 100%포인트다. 16개 시나리오 각각에서 취약 모드는 10/10 성공, 강화 모드는 0/10 성공이었다. 취약 모드 응답시간 중앙값은 128.11ms, 강화 모드는 120.86ms였다. 최대값은 각각 8827.02ms와 6989.76ms로 서버 초기 컴파일 영향이 포함된 이상치로 해석되며 보안 효과의 종속 변수로 사용하지 않았다.

가설대로 나온 부분은 모든 시나리오에서 강화 모드 성공률이 취약 모드보다 낮았다는 점이다. 가설과 다르게 나온 공격 성공 사례는 강화 모드에서 없었다. 다만 응답시간은 강화 모드가 더 느릴 것이라는 부가 예상과 달리 중앙값이 7.25ms 낮았다. 가능한 이유는 로컬 캐시·JIT·서버 준비 상태, 순서 교대, 단순 판정 경로 차이다. 현재 데이터는 응답시간 성능 우열을 결론 내리도록 설계되지 않았으므로 이 차이는 탐색적 관찰로만 남긴다.

초기 가설은 “보안 통제를 적용하면 웹 공격이 방어된다”였으나 범위와 측정값이 모호했다. 최종 가설은 16개 입력, 로컬 코드베이스, 공격 성공률, 두 모드를 명시하도록 수정했다. 원자료의 모드별 성공 건수와 시나리오별 10회 결과가 최종 판단의 직접 근거다.

## 5 논의

결과는 정의한 16개 공격 입력과 로컬 구현 범위에서 서버 측 통제가 공격 성공률을 낮춘다는 가설을 지지한다. 특히 클라이언트가 보낸 사용자 ID나 JWT 헤더를 신뢰하지 않고 서버가 소유권, 역할, 토큰 서명과 수명, 세션 상태, 요청 출처를 다시 검증하는 공통 원리가 모든 범주에서 작동했다. 차단 상태는 원인에 맞춰 401, 403, 410, 422, 429 등으로 나타났고, 이는 단순 UI 숨김이 아니라 서버 경계에서 요청이 거부됐음을 보여 준다.

그러나 본 실험의 공격 판정은 재현성을 위해 결정적으로 설계되어 같은 입력에 같은 결과를 낸다. 표본 10회는 실행 안정성을 확인하지만 인터넷 환경의 공격 확률을 추정하는 표본은 아니다. 단일 Windows 컴퓨터와 단일 Node.js 프로세스를 사용했고 속도 제한은 메모리 기반이므로 다중 인스턴스 환경을 검증하지 않았다. HTTP localhost에서는 Secure 쿠키의 실제 전송 조건을 완전히 재현하지 못했다. MFA, 유출 비밀번호 대규모 차단 목록, 키 회전, 다중 발급자, `nbf`, 분산 속도 제한은 포함하지 않았다. SQL 삽입, XSS, SSRF, 파일 업로드, 역직렬화, 공급망, 네트워크와 운영체제 공격도 연구 범위 밖이다. 따라서 “모든 공격을 방어했다”거나 “실서비스 침해가 0%가 된다”는 결론은 내릴 수 없다.

## 6 결론

동일한 16개 공격을 취약·강화 모드에 각각 10회 적용한 320건의 원자료에서 취약 모드는 160건 모두 공격이 성공했고 강화 모드는 160건 모두 차단됐다. 공격 성공률의 100%포인트 감소는 최종 가설을 지지한다. 이 결론은 서버 측 인증·세션·권한 통제의 적용 여부가 본 실험의 공격 성공 판정을 바꿨다는 범위로 제한된다. 후속 연구에서는 분산 저장소 기반 속도 제한, HTTPS 브라우저 쿠키 동작, 더 다양한 토큰 실패 조건, 독립 연구자가 작성한 변형 입력을 추가해야 한다.

## AI와 본인의 판단

AI는 후보 질문 정리, 코드와 테스트 초안, 반복 실행 자동화, 표와 문장 정리를 맡았다.  
본인은 최종 가설과 연구 범위를 선택하고 로컬 데이터베이스를 구성했으며, 어떤 결과를 근거로 결론을 받아들일지 판단했다.  
AI가 계산한 집계는 원자료 320건과 자동화 테스트로 다시 확인했고, 과도한 일반화를 제외하는 최종 판단은 본인이 수행했다.
